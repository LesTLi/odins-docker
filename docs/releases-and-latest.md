# Выпуски образов и latest

Исследовано 2026-10-27. Это инструкция и предложение политики latest,
а не реализованная публикация. Registry, latest и GitHub Releases в проекте
пока не подключены. Доставка TAR ограничена квотой GitHub Actions Artifacts.

## Что уже реализовано

В versions.env задаются IMAGE_VERSION=1.0, ONEC_VERSION=8.3.27.2130 и
INSTALL_FORMAT=deb (либо run). Для обоих способов установки разработческий
тег одинаков по структуре: onec-test:1.0-1c8.3.27.2130-b<run-id> и
onec-server:1.0-1c8.3.27.2130-b<run-id>. Формат сохраняется в labels и JSON.
Один запуск Actions выбирает только один формат из versions.env.

Push main запускает Check, но не сборку образов. Ручной запуск Build and test
на ветке создаёт разработческие образы. Временно сохранён автоматический
запуск на feat/images-actions при изменениях файлов сборки. Push Git-тега
v1.0, совпадающего с IMAGE_VERSION, запускает сборку выпуска. Ручной запуск
на этом Git-теге также создаёт выпуск. Итоговые теги:
onec-test:1.0-1c8.3.27.2130 и onec-server:1.0-1c8.3.27.2130.

Текущий workflow собирает и проверяет новый кандидат на Git-теге; он не
копирует предыдущий разработческий образ. В выпускной TAR включаются тег
точного запуска и итоговый тег одного образа. latest туда не добавляется.

## Как устроены общепринятые практики

Git-тег v1.0 выбирает коммит с рецептом сборки. Docker-тег
1.0-1c8.3.27.2130 обозначает выпуск. Docker-тег latest — изменяемое имя
выбранного образа по умолчанию. Registry manifest digest — идентификатор
точного содержимого образа в registry. latest и версионный тег могут
указывать на один artifact; latest не является ссылкой на другой тег.

Docker не вычисляет максимальную версию: отправка версии 1.1 сама по себе
не обновляет latest. Если тег не указан, Docker использует имя latest.
В Docker Official Images этот тег означает рекомендуемый вариант по
умолчанию, который может отличаться от самого нового по номеру выпуска.
Пример из официального определения Alpine на дату исследования:
3.24.3, 3.24, 3, latest перечислены вместе для одного выпуска исходников.

В CI распространено назначать теги по Git-событиям: ветке, Git-тегу, SHA.
Официальный пример Docker генерирует несколько тегов для одной сборки.
Это общая модель, но не обязательный для всех проектов процесс выпуска.
Наши два числа IMAGE_VERSION — собственная схема, а не полный SemVer.

## Два варианта назначения latest

1. Автоматически при выпуске стабильной версии. Git-тег запускает сборку,
   проверки проходят, workflow назначает этому же образу версионный тег и
   latest. Отдельная сборка latest не нужна. Автоматика должна учитывать,
   какой выпуск выбран актуальным: повтор старого workflow или выпуск
   исправления старой ветки не должен случайно отодвинуть latest назад.
2. Отдельное продвижение готового выпуска. Сначала выпускается образ с
   конкретной версией. После проверки конфигурации 1С в Jenkins владелец
   выбирает этот образ как рекомендуемый; ему добавляют latest без
   пересборки. В registry такую операцию можно автоматизировать отдельным
   workflow с явным выбором версии/digest и подтверждением выпуска.

Для этого проекта предлагается второй вариант: smoke-тесты инструментов
не заменяют проверку пользовательской конфигурации 1С с лицензией.
Пока latest не подтверждён как функция, ни один вариант не реализован.

## Последовательность работы при втором варианте

1. Изменить код и versions.env на ветке; вручную собрать разработческий
   образ. Проверить результат с тегом b<run-id>.
2. После проверки объединить изменения в main. В main выполняется Check.
3. Для первого выпуска установить IMAGE_VERSION=1.0, зафиксировать изменения
   и создать Git-тег v1.0 на выбранном проверенном коммите. Push тега
   запускает сборку и тестирование нового выпускного кандидата.
4. Скачать выпускной TAR и проверить SHA256. Загрузить его через docker load.
   Он содержит конкретную версию 1.0-1c8.3.27.2130; latest пока отсутствует.
5. Когда Harbor будет готов, отправить эту конкретную версию в registry и
   проверить именно её в Jenkins на реальной конфигурации.
6. После принятия версии назначить тому же готовому образу latest и отправить
   этот тег в registry. На этом шаге latest обновляется без docker build.
7. Следующий выпуск получает IMAGE_VERSION=1.1 и Git-тег v1.1. Пока он
   проверяется, latest может оставаться на 1.0. После принятия 1.1 latest
   переносится на него; конкретная версия 1.0 сохраняется для отката.

| Событие | Конкретные версии | latest |
| --- | --- | --- |
| Выпущен и принят 1.0 | 1.0 → образ A | образ A |
| Выпущен 1.1, идёт проверка | 1.0 → A, 1.1 → B | образ A |
| Принят 1.1 | 1.0 → A, 1.1 → B | образ B |

Для отката можно снова назначить latest сохранённому образу A. Пересборка
не нужна. Уже работающие контейнеры от изменения тега не перезапускаются.
Для воспроизводимых запусков Jenkins лучше выбирать конкретный защищённый
тег или digest; latest удобен, если намеренно нужен текущий рекомендуемый
выпуск. Новый рекомендуемый выпуск может содержать другую версию 1С.

## Пример будущей ручной загрузки в Harbor

Команды ниже — инструкция, они не выполнялись. harbor.example.com и проект
onec — примеры; проект должен быть заранее создан в Harbor. Команды для
Linux shell, из каталога с распакованным artifact:

```bash
sha256sum --check onec-test_1.0-1c8.3.27.2130_linux-amd64.tar.sha256
docker load --input onec-test_1.0-1c8.3.27.2130_linux-amd64.tar
docker login harbor.example.com
docker tag onec-test:1.0-1c8.3.27.2130 harbor.example.com/onec/onec-test:1.0-1c8.3.27.2130
docker push harbor.example.com/onec/onec-test:1.0-1c8.3.27.2130
```

После принятия именно этого образа в Jenkins, в том же Docker daemon:

```bash
docker tag harbor.example.com/onec/onec-test:1.0-1c8.3.27.2130 harbor.example.com/onec/onec-test:latest
docker push harbor.example.com/onec/onec-test:latest
```

Обе команды используют явный исходный версионный тег. Если продвижение
выполняется на другом компьютере, сначала нужно получить конкретный образ
из registry, предпочтительно по проверенному digest. Для onec-server
выполнить аналогичные действия со своим TAR и именем repository.

Проверка результата публикации:

```bash
docker buildx imagetools inspect harbor.example.com/onec/onec-test:1.0-1c8.3.27.2130
docker buildx imagetools inspect harbor.example.com/onec/onec-test:latest
```

Сравнить поле Digest: оба тега должны разрешаться в один manifest digest.
SHA256 TAR и локальный image ID из metadata JSON — другие идентификаторы,
их нельзя сравнивать с registry manifest digest как равные значения.

В Harbor рекомендуется защитить конкретные выпускные теги от перезаписи,
а latest оставить изменяемым. Имя с номером само по себе не делает тег
immutable. Повторная сборка того же коммита может изменить байты из-за
обновления базового образа и APT-зависимостей. Для исправленного выпуска
наша политика — новый IMAGE_VERSION и новый Git-тег, а не замена старого.
